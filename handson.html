4. 연결 확인

exercises/03-prompt-llm.ipynb 의 첫 셀을 실행합니다. 이 셀은 AI Core를 아직 호출하지 않고, 입력한 연결 값이 코드에서 제대로 읽히는지만 확인합니다.

import init_env
import variables
import importlib
init_env = importlib.reload(init_env)        # variables.py 를 방금 수정했으면 reload 로 다시 읽음
variables = importlib.reload(variables)

init_env.set_environment_variables()         # variables.py 값을 환경변수로 세팅 (SDK가 여기서 읽음)

print(f"Resource group: {variables.RESOURCE_GROUP}")
print(f"Embedding deployment ID: {variables.EMBEDDING_DEPLOYMENT_ID}")
print(f"LLM deployment ID: {variables.LLM_DEPLOYMENT_ID}")
print(f"Orchestration URL: {variables.AICORE_ORCHESTRATION_DEPLOYMENT_URL}")

한 줄씩 무슨 일이 일어나나요?

코드 하는 일
import variables 내가 값을 적어둔 variables.py 를 불러옴
importlib.reload(...) 값을 방금 바꿨을 때 노트북이 옛 값을 기억하지 않도록 다시 읽음
init_env.set_environment_variables() variables.py 의 값을 환경변수로 올려, SDK가 자동으로 집어감
print(...) 값이 제대로 들어왔는지 눈으로 확인

💡 None 이 출력되면 해당 값이 variables.py 에 비어 있다는 뜻입니다. 값을 채우고 셀을 다시 실행하세요 (reload 덕분에 재시작 없이 반영됩니다).

모듈 1 · LLM 프롬프트 기초

🎯 목표: SDK로 LLM을 호출하고, role·환각·멀티모달을 이해한다. ⏱️ 시간: 약 35분 📓 기반: 03-prompt-llm.ipynb

배경 — LLM과 "프롬프트"

LLM(대형 언어 모델) 은 지금까지의 대화를 보고 다음에 올 가장 그럴듯한 말을 생성하는 모델입니다. 우리가 모델에 보내는 입력을 프롬프트(prompt) 라고 부릅니다.

프롬프트는 보통 메시지 목록으로 보냅니다. 각 메시지에는 역할(role) 이 붙습니다.

role 의미 예시
system 모델의 성격·규칙 설정 "너는 친절한 SAP 상담원이다"
user 사람의 질문/요청 "AI Core가 뭐야?"
assistant 모델의 이전 답변 (대화를 이어갈 때) (모듈 6 메모리에서 사용)

이 모듈에서는 ① 기본 호출 → ② role로 어조 바꾸기 → ③ 환각 관찰 → ④ 이미지 입력(멀티모달) 순서로 체험합니다.

1. 기본 chat 호출

가장 단순한 형태입니다. user 메시지 하나만 보내고 답을 받습니다.

from gen_ai_hub.proxy.native.openai import chat

MODEL_NAME = 'gpt-5.6-sol'   # 배포된 모델명으로 (강사 안내 값)

messages = [
    {"role": "user", "content": "What is the underlying model architecture of an LLM? Explain it as short as possible."}
]
response = chat.completions.create(model_name=MODEL_NAME, messages=messages)
print(response.choices[0].message.content)

코드 뜯어보기

  • from ... import chat : Gen AI Hub가 제공하는 OpenAI 호환 chat 인터페이스를 가져옵니다. 모델이 Claude든 GPT든 같은 방식으로 부릅니다.
  • MODEL_NAME : 어떤 배포(모델)를 쓸지 지정. 이 한 줄만 바꾸면 다른 모델로 전환됩니다.
  • messages : 위에서 설명한 메시지 목록.
  • response.choices[0].message.content : 모델의 답변 텍스트. 응답은 여러 후보(choices)를 담을 수 있어 보통 첫 번째([0])를 봅니다.

2. role 이해 — system 프롬프트로 스타일 제어

이번엔 system 메시지를 추가합니다. 질문은 그대로인데 어조가 어떻게 바뀌는지 보세요.

messages = [
    {"role": "system", "content": "Speak like Yoda from Star Wars."},
    {"role": "user", "content": "What is the underlying model architecture of an LLM? Explain it as short as possible."},
]
response = chat.completions.create(model_name=MODEL_NAME, messages=messages)
print(response.choices[0].message.content)
  • system: 모델의 역할·규칙·어조를 정의 (여기선 "요다처럼 말하라")
  • user: 실제 질문 (내용은 1번과 동일)
  • (assistant: 이전 모델 답변 — 모듈 6 메모리에서 활용)

💡 포인트: system 은 "모델에게 미리 주는 지시서"입니다. 어조뿐 아니라 "반드시 한국어로", "3문장 이내로", "표로 정리" 같은 출력 형식도 여기서 통제합니다.

3. 환각(Hallucination) 관찰

이제 일부러 모델이 잘 모를 만한 SAP 내부 동작을 물어봅니다.

messages = [
    {"role": "system", "content": "You are an SAP Consultant."},
    {"role": "user", "content": "How does the data masking of the orchestration service work?"},
]
response = chat.completions.create(model_name=MODEL_NAME, messages=messages)
print(response.choices[0].message.content)

답변이 그럴듯하지만 세부가 틀릴 수 있습니다. 모델은 "모른다"고 하기보다 지어내는 경향이 있는데, 이를 환각(hallucination) 이라고 합니다.

🔑 이 순간을 기억하세요. 지금 받은 "그럴듯하지만 미심쩍은" 답을, 모듈 4(그라운딩) 에서 똑같은 질문으로 다시 던져 비교합니다. 그라운딩이 환각을 어떻게 줄이는지 직접 확인하게 됩니다. 가능하면 지금 답변을 메모해두세요.

4. 멀티모달 — 이미지 입력

멀티모달이란 텍스트뿐 아니라 이미지도 함께 입력하는 것입니다. 모델에게 그림을 "보여주고" 설명을 받습니다.

import base64

# 이미지는 그대로 못 보내므로 base64 문자열로 인코딩해서 보냄
with open("documents/ai-foundation-architecture.png", "rb") as f:
    image_data = base64.b64encode(f.read()).decode("utf-8")

messages = [{"role": "user", "content": [
    {"type": "text", "text": "Describe the image as an alternative text."},
    {"type": "image_url", "image_url": {"url": f"data:image/png;base64,{image_data}"}},
]}]
response = chat.completions.create(model_name=MODEL_NAME, messages=messages)
print(response.choices[0].message.content)

코드 뜯어보기

  • base64.b64encode(...) : 이미지 파일을 텍스트(문자열)로 변환합니다. API는 바이너리 대신 이 문자열을 받습니다.
  • content 가 리스트로 바뀌었습니다 → 텍스트 + 이미지를 한 메시지에 함께 담은 형태입니다.
  • "type": "image_url" + data:image/png;base64,... : "이건 PNG 이미지이고 내용은 이 문자열이다"라고 알려주는 형식입니다.

이미지에서 텍스트/표를 구조화해서 뽑을 수도 있습니다. 예를 들어 documents/bananabread.png(요리 레시피 이미지)로 재료·조리법을 JSON으로 추출해보세요 — 영수증·송장·명함 처리 같은 실무로 바로 이어집니다.

직접 바꿔보기 (실험)

  • system 프롬프트: "초등학생에게 설명하듯", "반드시 3문장으로" 등으로 톤·길이 제어
  • 모델 교체: MODEL_NAME 을 gpt-5.6-sol, anthropic--claude-4.6-sonnet, gpt-5 로 바꿔 응답·속도·어조 비교
  • temperature: create(..., temperature=0.2) 과 1.5 를 각각 여러 번 실행해 일관성 차이 (⚠️ GPT-5 계열(gpt-5.6-sol 등)은 temperature=0 을 거부하니 0.2 이상 사용)
  • 환각 교정 시도: system에 "모르면 모른다고 답하라"를 추가 → 어떻게 바뀌는지
  • 멀티모달 응용: bananabread.png 로 재료·조리법을 2개 JSON으로 추출

✅ 체크포인트

  • chat 호출로 답변을 받았다
  • system 프롬프트로 어조가 바뀌는 걸 확인했다
  • 환각 사례를 하나 관찰했다
  • 모델명 한 줄 교체로 다른 모델이 응답하는 걸 확인했다

모듈 2 · 임베딩 & 벡터 유사도

🎯 목표: 텍스트를 임베딩(벡터)으로 바꾸고, 의미 유사도를 계산한다. ⏱️ 시간: 약 30분 📓 기반: 04-create-embeddings.ipynb

배경 — 임베딩이 왜 중요한가

임베딩(embedding) 은 텍스트를 숫자 벡터(숫자들의 긴 목록)로 바꾼 것입니다. 핵심 아이디어는 하나입니다.

의미가 비슷한 텍스트는 벡터 공간에서 가깝게 놓인다.

예를 들어 "apple"과 "orange"는 가깝고(둘 다 과일), "apple"과 "phone"은 상대적으로 멉니다. 컴퓨터는 글자 뜻을 모르지만, 벡터 사이의 거리로 "의미의 가까움"을 계산할 수 있습니다.

"apple"  → [0.02, -0.41, 0.88, ... ]   ┐
"orange" → [0.05, -0.39, 0.81, ... ]   ├─ 가까움 (둘 다 과일)
"phone"  → [0.77,  0.12, -0.33, ...]   ┘   멀다

이 모듈에서 쓰는 text-embedding-3-small 모델은 어떤 텍스트든 1536개의 숫자(= 1536차원 벡터)로 바꿉니다.

🔗 다음 모듈과의 연결: 이 "가까움"이 바로 RAG/그라운딩의 검색 원리입니다. 질문을 임베딩하고, 저장소에서 벡터가 가까운 문서 조각을 찾아 프롬프트에 넣는 것 — 그게 모듈 4·5에서 할 일입니다.

1. 임베딩 생성

import init_env
init_env.set_environment_variables()

from gen_ai_hub.proxy.native.openai import embeddings
EMBEDDING_MODEL_NAME = "text-embedding-3-small"

def get_embedding(input_text):
    response = embeddings.create(input=input_text, model_name=EMBEDDING_MODEL_NAME)
    return response.data[0].embedding

apple_embedding   = get_embedding("apple")
orange_embedding  = get_embedding("orange")
phone_embedding   = get_embedding("phone")
dog_embedding     = get_embedding("I love dogs")
animals_embedding = get_embedding("I love animals")
cat_embedding     = get_embedding("I hate cats")

print(len(apple_embedding), "dimensions")

2. 코사인 유사도 — ⚠️ 버그 수정 과제

두 벡터가 얼마나 가까운지를 재는 대표적인 방법이 코사인 유사도(cosine similarity) 입니다. 1에 가까울수록 비슷, 0에 가까울수록 무관합니다. (두 벡터가 이루는 각도로 생각하면 됩니다 — 각도가 작을수록 유사.)

노트북에는 일부러 틀린 함수가 들어 있습니다. 두 벡터가 아니라 같은 벡터를 비교하고 있습니다.

from scipy import spatial

# 버그 버전 (항상 1.0을 반환함 — 왜일까?)
def get_cosine_similarity(vector_1, vector_2):
    return 1 - spatial.distance.cosine(vector_1, vector_1)   # ← vector_1 두 번!

🐞 왜 항상 1.0일까? spatial.distance.cosine(a, a) 는 자기 자신과의 거리 = 0 입니다. 그래서 1 - 0 = 1.0 이 되어, 무엇을 넣어도 "완전히 똑같다(1.0)"고 나옵니다. 두 번째 인자가 vector_1 로 잘못 들어간 게 원인입니다.

직접 고쳐보세요. 정답:

def get_cosine_similarity(vector_1, vector_2):
    return 1 - spatial.distance.cosine(vector_1, vector_2)   # ← 두 번째는 vector_2

3. 유사도 비교

print("apple-orange:", get_cosine_similarity(apple_embedding, orange_embedding))
print("apple-phone :", get_cosine_similarity(apple_embedding, phone_embedding))
print("dog-animals :", get_cosine_similarity(dog_embedding, animals_embedding))
print("dog-cat     :", get_cosine_similarity(dog_embedding, cat_embedding))

결과 읽는 법: 의미가 가까운 쌍일수록 값이 큽니다.

  • apple-orange > apple-phone → 과일끼리가 과일-전화기보다 가깝다 ✅
  • dog-animals > dog-cat → "개를 좋아해"는 "동물을 좋아해"와 가깝고, "고양이를 싫어해"와는 상대적으로 멀다 ✅

📌 숫자의 절대값(예: 0.8)보다 쌍들 사이의 상대적 크기(어느 쌍이 더 큰가)를 보는 게 핵심입니다. 바로 이 "더 가까운 것 찾기"가 검색의 원리입니다.

직접 바꿔보기 (실험)

  • 본인 도메인 단어들("인보이스", "청구서", "주문서", "날씨")을 임베딩해 유사도 매트릭스 만들기
  • 한국어 vs 영어 같은 의미 단어의 유사도 ("dog" vs "개")
  • 긴 문장끼리 vs 단어끼리 유사도 비교
  • text-embedding-3-small 외 다른 임베딩 모델이 배포돼 있으면 차원 수·결과 비교

✅ 체크포인트

  • 임베딩 차원 수(1536)를 확인했다
  • 버그 함수를 고쳤다
  • 의미가 가까운 쌍이 더 높은 유사도를 갖는 걸 확인했다

모듈 3 · Orchestration + 콘텐츠 필터 + 데이터 마스킹

🎯 목표: 여러 모듈을 하나의 config로 엮는 Orchestration을 구성하고, 입력·출력 콘텐츠 필터와 PII 데이터 마스킹을 적용한다. ⏱️ 시간: 약 50분 📓 기반: 08-orchestration-service.ipynb + SAP BTP AI Best Practices(data-masking)

배경 — Orchestration은 "조립 설정"이다

지금까지(모듈 1)는 모델을 직접 불렀습니다. 하지만 실무에서는 모델 호출 전후로 할 일이 많습니다 — 프롬프트 템플릿 채우기, 개인정보 가리기, 문서 검색해서 끼워넣기, 유해 내용 거르기.

Orchestration은 이 단계들을 하나의 설정(config) 으로 선언하고, 그 설정대로 파이프라인을 돌립니다.

입력 → [템플릿] → [마스킹] → [그라운딩] → [LLM] → [출력 필터] → 결과
         (3번)     (6번)      (모듈4)      택1       (5번)
  • 각 단계는 선택적입니다. 이 모듈에선 템플릿 → 필터 → 마스킹을 하나씩 켜봅니다.
  • 가장 큰 장점: 파이프라인은 그대로 두고 LLMModelDetails(name=...) 한 줄만 바꿔 모델을 교체할 수 있습니다.

🧩 용어: 각 단계를 모듈(module) 이라 부르고, 그 모듈들을 묶은 게 OrchestrationConfig 입니다. "모듈을 config에 꽂는다"는 표현이 반복됩니다.

⚠️ SDK 네임스페이스가 orchestration_v2 입니다. orchestration(v1 없는 버전)으로 쓰면 import 에러가 납니다 — Copilot이 자주 틀리는 지점이니 주의하세요.

1. import & 모델·템플릿

import init_env, variables
init_env.set_environment_variables()

from gen_ai_hub.orchestration_v2.models.llm_model_details import LLMModelDetails
from gen_ai_hub.orchestration_v2.models.message import SystemMessage, UserMessage
from gen_ai_hub.orchestration_v2.models.template import Template, PromptTemplatingModuleConfig
from gen_ai_hub.orchestration_v2.models.config import ModuleConfig, OrchestrationConfig
from gen_ai_hub.orchestration_v2.service import OrchestrationService
from gen_ai_hub.orchestration_v2.exceptions import OrchestrationError

llm = LLMModelDetails(name="gpt-5.6-sol", params={"max_tokens": 5000, "temperature": 1})

template = Template(
    template=[
        SystemMessage(content="You are a helpful translation assistant."),
        UserMessage(content="Translate the following text to {{?to_lang}}: {{?user_query}}"),
    ],
    defaults={"to_lang": "English"},
)

코드 뜯어보기

  • LLMModelDetails(name=..., params=...) : 어떤 모델을, 어떤 옵션(max_tokens, temperature)으로 쓸지 정의합니다.
  • Template(template=[SystemMessage, UserMessage]) : 모듈 1의 메시지 목록과 같은 개념인데, 재사용 가능한 틀로 만들었습니다.
  • {{?user_query}}, {{?to_lang}} : 플레이스홀더(빈칸)입니다. 실행할 때 실제 값으로 채웁니다.
  • defaults={"to_lang": "English"} : 값을 안 주면 기본으로 "English"를 씀 → 매번 안 넘겨도 됩니다.

💡 왜 템플릿을 쓰나? 프롬프트를 코드 곳곳에 흩어 쓰지 않고 한 곳에 모아, 값만 바꿔 재사용하기 위해서입니다. 번역 대상 언어나 질문만 바꾸면 같은 틀이 돕니다.

2. config 조립 & 실행

prompt_template = PromptTemplatingModuleConfig(prompt=template, model=llm)
config = OrchestrationConfig(modules=ModuleConfig(prompt_templating=prompt_template))

service = OrchestrationService(
    api_url=variables.AICORE_ORCHESTRATION_DEPLOYMENT_URL,
    config=config,
)
result = service.run(placeholder_values={"user_query": "Geht das wirklich mit allen Modellen?"})
print(result.final_result.choices[0].message.content)

코드 뜯어보기

  • PromptTemplatingModuleConfig(prompt=..., model=...) : 템플릿 + 모델을 묶어 "프롬프트 모듈" 로 만듭니다.
  • OrchestrationConfig(modules=ModuleConfig(prompt_templating=...)) : 모듈들을 담는 전체 설정. 지금은 프롬프트 모듈 하나뿐입니다.
  • service.run(placeholder_values={...}) : 플레이스홀더를 실제 값으로 채워 실행. 여기선 독일어 문장을 넘겨 영어로 번역시킵니다.
  • result.final_result.choices[0].message.content : 모듈 1과 비슷하지만, Orchestration은 중간 단계 결과도 담기에 최종 답은 final_result 아래에 있습니다.

🔁 앞으로의 패턴: "① 모듈 하나를 더 만든다 → ② ModuleConfig 에 꽂는다 → ③ service.config 를 교체한다 → ④ 다시 run." 아래 3~6번이 전부 이 패턴입니다.

3. 입력 콘텐츠 필터 추가

콘텐츠 필터는 혐오·폭력·자해·성적 표현 같은 유해 콘텐츠를 걸러냅니다. 입력 필터는 사용자가 보낸 프롬프트를, 출력 필터는 모델이 생성한 답변을 검사합니다. 아래에서는 입력 필터부터 켭니다. 두 종류의 필터 제공자를 함께 씁니다 — Azure Content Safety와 Llama Guard.

from gen_ai_hub.orchestration_v2.models.content_filtering import (
    FilteringModuleConfig, InputFiltering, OutputFiltering)
from gen_ai_hub.orchestration_v2.models.content_filter import ContentFilter, ContentFilterProvider
from gen_ai_hub.orchestration_v2.models.azure_content_filter import AzureContentFilter, AzureThreshold
from gen_ai_hub.orchestration_v2.models.llama_guard_3_filter import LlamaGuard38bFilter

input_filter = ContentFilter(type=ContentFilterProvider.AZURE,
    config=AzureContentFilter(hate=AzureThreshold.ALLOW_SAFE, violence=AzureThreshold.ALLOW_SAFE,
                              self_harm=AzureThreshold.ALLOW_SAFE, sexual=AzureThreshold.ALLOW_SAFE))
input_filter_llama = ContentFilter(type=ContentFilterProvider.LLAMA_GUARD_3_8B,
    config=LlamaGuard38bFilter(hate=True))

config_with_filter = OrchestrationConfig(modules=ModuleConfig(
    prompt_templating=prompt_template,
    filtering=FilteringModuleConfig(input=InputFiltering(filters=[input_filter, input_filter_llama])),
))
service.config = config_with_filter

코드 뜯어보기

  • AzureThreshold.ALLOW_SAFE : "안전한 것만 통과" = 가장 엄격. 뒤에서 ALLOW_SAFE_LOW → ALLOW_SAFE_LOW_MEDIUM → ALLOW_ALL 로 갈수록 느슨해집니다.
  • hate / violence / self_harm / sexual : 네 가지 유해 카테고리를 각각 따로 조절할 수 있습니다.
  • 필터를 리스트로 여러 개 넣으면 하나라도 걸리면 차단됩니다 (Azure + Llama Guard 동시 적용).
  • service.config = config_with_filter : 서비스에 새 설정을 꽂아 교체 (위에서 말한 패턴 ③).

4. 필터 테스트

try:
    result = service.run(placeholder_values={"user_query": "Du bist ein ganz mieser Entwickler!"})
    print(result.final_result.choices[0].message.content)
except OrchestrationError as e:
    print("차단됨:", e.message)

# 정상 프롬프트는 통과
result = service.run(placeholder_values={"user_query": "Du bist ein super talentierter Entwickler!"})
print(result.final_result.choices[0].message.content)

무슨 일이 일어나나요?

  • 첫 번째 문장("너는 아주 형편없는 개발자야!")은 공격적 → 입력 필터가 차단 → OrchestrationError 발생 → except 로 잡아 "차단됨" 출력.
  • 두 번째 문장("너는 정말 재능 있는 개발자야!")은 안전 → 통과 → 정상 번역 결과 출력.

💡 try/except 로 감싸는 이유: 차단되면 예외(에러) 로 알려주기 때문입니다. 감싸지 않으면 노트북 셀이 빨간 에러로 멈춥니다.

5. 출력 필터도 추가

output_filter = ContentFilter(type=ContentFilterProvider.AZURE,
    config=AzureContentFilter(hate=AzureThreshold.ALLOW_SAFE, violence=AzureThreshold.ALLOW_SAFE_LOW,
                              self_harm=AzureThreshold.ALLOW_SAFE_LOW_MEDIUM, sexual=AzureThreshold.ALLOW_ALL))

config_with_io = OrchestrationConfig(modules=ModuleConfig(
    prompt_templating=prompt_template,

6. 데이터 마스킹 (PII 익명화)

필터가 "유해 콘텐츠"를 막는다면, 마스킹은 개인정보(PII)를 모델에 보내기 전에 가립니다. 같은 Orchestration config에 masking 모듈을 추가합니다.

from gen_ai_hub.orchestration_v2.models.data_masking import (
    MaskingModuleConfig, MaskingProviderConfig, MaskingMethod,
    DataMaskingProviderName, DPIStandardEntity, ProfileEntity)

masking = MaskingModuleConfig(masking_providers=[MaskingProviderConfig(
    type_=DataMaskingProviderName.SAP_DATA_PRIVACY_INTEGRATION,
    method=MaskingMethod.ANONYMIZATION,        # 또는 PSEUDONYMIZATION
    entities=[
        DPIStandardEntity(type=ProfileEntity.EMAIL),
        DPIStandardEntity(type=ProfileEntity.PHONE),
        DPIStandardEntity(type=ProfileEntity.PERSON),
    ],
)])

config_with_masking = OrchestrationConfig(modules=ModuleConfig(
    prompt_templating=prompt_template,
    masking=masking,
))
service.config = config_with_masking

result = service.run(placeholder_values={
    "user_query": "내 이름은 홍길동이고 이메일은 gildong@example.com 입니다. 요약해줘."
})
print(result.final_result.choices[0].message.content)
  • ANONYMIZATION: PII를 MASKED_PERSON 등으로 익명화 (복원 불가)
  • PSEUDONYMIZATION: 가명으로 치환 (매핑으로 복원 가능)
  • ProfileEntity: EMAIL, PHONE, PERSON, ORG, LOCATION, ADDRESS, CREDIT_CARD_NUMBER, IBAN, SSN 등

마스킹·필터·그라운딩을 한 ModuleConfig 에 모두 넣으면 "규정 준수형" 파이프라인이 됩니다.

직접 바꿔보기 (실험)

  • 마스킹 ANONYMIZATION ↔ PSEUDONYMIZATION 전환 후 출력 차이 비교
  • entities 에 ProfileEntity.ORG, ADDRESS, CREDIT_CARD_NUMBER 등을 추가
  • AzureThreshold 를 ALLOW_SAFE → ALLOW_SAFE_LOW → ALLOW_SAFE_LOW_MEDIUM → ALLOW_ALL 로 낮추며 차단 경계 찾기
  • hate/violence/self_harm/sexual 카테고리를 각각 조절
  • Azure만 / Llama Guard만 / 둘 다 켰을 때 판정 차이

모듈 4 · Document Grounding + Streaming

🎯 목표: Orchestration에 그라운딩 모듈을 붙여 근거 기반 답변을 만들고, 스트리밍으로 받는다. ⏱️ 시간: 약 40분 📓 기반: 09-orchestration-service-grounding.ipynb

배경 — 그라운딩 = 관리형 RAG

모듈 1에서 모델이 환각(그럴듯한 거짓)을 내는 걸 봤습니다. 이를 줄이는 가장 효과적인 방법이 RAG입니다.

RAG: 모델에게 바로 묻지 않고, ① 질문과 관련된 문서를 먼저 검색해서 ② 그 내용을 프롬프트에 같이 넣어 묻는 것. 모델은 "주어진 근거 안에서" 답하므로 환각이 줄고 출처가 생깁니다.

Document Grounding은 이 RAG를 SAP가 관리형으로 제공합니다. 직접 임베딩·벡터DB·검색을 구현하지 않아도, 저장소만 지정하면 검색·주입을 대신 해줍니다. 이 모듈에서는 공개 저장소 help.sap.com 을 씁니다.

동작 흐름

질문(user_query)
   → [그라운딩] help.sap.com 에서 관련 청크 검색
   → 검색 결과를 grounding_response 에 담음
   → [템플릿] "Context:" 자리에 그 결과를 끼워넣음
   → [LLM] 질문 + Context 를 함께 보고 답변

즉 input 플레이스홀더(질문)로 검색하고, 결과를 output 플레이스홀더(grounding_response)로 돌려받아 템플릿의 Context: 자리에 자동으로 채웁니다.

1. 모델 + 템플릿

import init_env, variables
init_env.set_environment_variables()

from gen_ai_hub.orchestration_v2.models.llm_model_details import LLMModelDetails
from gen_ai_hub.orchestration_v2.models.config import ModuleConfig, OrchestrationConfig
from gen_ai_hub.orchestration_v2.models.document_grounding import (
    DocumentGroundingFilter, DocumentGroundingConfig,
    DocumentGroundingPlaceholders, GroundingModuleConfig)
from gen_ai_hub.orchestration_v2.models.template import Template, PromptTemplatingModuleConfig
from gen_ai_hub.orchestration_v2.models.message import SystemMessage, UserMessage
from gen_ai_hub.orchestration_v2.service import OrchestrationService

llm = LLMModelDetails(name="gpt-5.6-sol")

template = Template(template=[
    SystemMessage(content="You are a helpful assistant."),
    UserMessage(content="""Answer the request by providing relevant answers that fit to the request.
        Request: {{?user_query}}
        Context: {{?grounding_response}}
        """),
])

템플릿의 두 플레이스홀더에 주목하세요.

  • {{?user_query}} : 내가 넣을 질문.
  • {{?grounding_response}} : 내가 채우지 않습니다! 그라운딩 모듈이 검색 결과로 자동으로 채워주는 자리입니다.

💡 그래서 service.run() 에서 grounding_response 는 안 넘기고 user_query 만 넘깁니다. 나머지는 그라운딩이 알아서 합니다.

2. 그라운딩 config

filters = [DocumentGroundingFilter(id="SAPHelp", data_repository_type="help.sap.com")]

grounding_config = GroundingModuleConfig(config=DocumentGroundingConfig(
    filters=filters,
    placeholders=DocumentGroundingPlaceholders(input=["user_query"], output="grounding_response"),
))

prompt_template = PromptTemplatingModuleConfig(prompt=template, model=llm)
config = OrchestrationConfig(modules=ModuleConfig(
    prompt_templating=prompt_template, grounding=grounding_config))

service = OrchestrationService(api_url=variables.AICORE_ORCHESTRATION_DEPLOYMENT_URL, config=config)
resp = service.run(placeholder_values={"user_query": "What is Joule?"})
print(resp.final_result.choices[0].message.content)

코드 뜯어보기

  • DocumentGroundingFilter(id="SAPHelp", data_repository_type="help.sap.com") : 어디서 검색할지 지정. 여기선 공개 SAP Help.
  • DocumentGroundingPlaceholders(input=["user_query"], output="grounding_response") : 무엇으로 검색하고(input=질문), 어디에 결과를 담을지(output=템플릿의 Context 자리) 연결.
  • grounding=grounding_config : 그라운딩 모듈을 config에 꽂음 (모듈 3의 패턴 그대로).
  • run(placeholder_values={"user_query": "What is Joule?"}) : 질문만 넘기면 검색→주입→답변이 한 번에 일어납니다.

3. 스트리밍

스트리밍은 답을 다 만든 뒤 한꺼번에 받는 대신, 생성되는 토큰을 실시간으로 흘려받는 방식입니다. ChatGPT가 글자를 또르륵 찍어내는 그 느낌 — 체감 응답 속도가 빨라집니다.

from gen_ai_hub.orchestration_v2.models.streaming import GlobalStreamOptions

stream_config = OrchestrationConfig(
    modules=ModuleConfig(prompt_templating=prompt_template, grounding=grounding_config),
    stream=GlobalStreamOptions(enabled=True))

for chunk in service.stream(config=stream_config,
                            placeholder_values={"user_query": "What is Joule?"}):
    delta = chunk.final_result.choices[0].delta.content
    if delta:
        print(delta, end="", flush=True)

코드 뜯어보기

  • GlobalStreamOptions(enabled=True) : 스트리밍 켜기.
  • service.stream(...) : run 대신 반복(for문)으로 조각(chunk)을 받습니다.
  • delta.content : 이번 조각에서 새로 추가된 글자. (message.content 전체가 아니라 증분)
  • print(delta, end="", flush=True) : 줄바꿈 없이 이어 붙여 바로바로 화면에 출력.

모듈 5 · 내 문서 그라운딩 (AI Core Grounding)

🎯 목표: 내 문서를 AI Core의 관리형 Grounding(벡터 저장소) 에 올려두고, 모듈 4 코드에서 필터만 바꿔 SDK로 질의한다. ⏱️ 시간: 약 35분 📓 기반: 노트북 07(Grounding Management) + 09(SDK 소비)

배경 — 소스만 바꾸면 "내 문서 챗봇"

모듈 4는 공개 저장소 help.sap.com 에 그라운딩했습니다. 하지만 실무에서 진짜 필요한 건 우리 회사 문서(매뉴얼·규정·제품 스펙)에 기반한 답변이죠. 이 모듈은 같은 메커니즘을 내 문서에 적용합니다.

좋은 소식: 벡터 데이터베이스(HANA 등)를 직접 구축할 필요가 없습니다. AI Core가 관리하는 벡터 저장소에 문서를 한 번 넣어두면, 청킹(문서 쪼개기)·임베딩·검색을 AI Core가 알아서 해줍니다.

① 수집 (강사가 사전 수행)
   내 문서(PDF 등) → AI Core Grounding 벡터 저장소에 적재
                     (문서 쪼개기 + 임베딩은 AI Core가 수행)

② 질의 (여러분이 실습)
   모듈 4 코드에서 grounding 필터만 '내 저장소'로 지정 → SDK로 호출

핵심은 "코드는 모듈 4와 거의 같고, 그라운딩 필터만 바뀐다" 입니다. data_repository_type 을 help.sap.com → vector 로, 그리고 내 저장소 id를 지정하는 것뿐입니다.

이 과정의 문서 묶음(corpus)은 documents/ 폴더의 SDK 레퍼런스 PDF들입니다. 모듈 4(공개)와 같은 질문을 던져 "내 문서 기반 답변"이 어떻게 다른지 비교해보세요.

Part A. 저장소 준비 (대부분 강사가 사전 완료)

단일 공유 AI Core 환경에서는 강사가 공유 벡터 저장소 1개를 미리 만들고 문서를 수집해 둔 뒤, 저장소 id를 공유합니다. 참가자는 그 id만 받으면 됩니다.

수집(ingestion)은 Grounding Vector API(REST)로 합니다. 강사는 저장소 폴더의 ingest_documents.py(저장소 생성 → PDF 청킹 → 수집 → 검색 확인)를 한 번 실행해 두고, 출력된 collection id 를 공유합니다. 그래서 참가자 실습은 질의(SDK) 에 집중합니다.

받을 값: GROUNDING_REPOSITORY_ID (= 수집으로 만든 collection id, 강사 공유)

Part B. 내 저장소에 SDK로 질의

모듈 6 · 메모리 챗봇

🎯 목표: 대화 맥락(history)을 유지하는 챗봇을 Orchestration으로 만든다. ⏱️ 시간: 약 20분 (마무리 포함 시 여유 조절) 📓 기반: 10-chatbot-with-memory.ipynb

배경 — LLM은 사실 "기억"이 없다

놀랍게도 LLM은 이전 호출을 기억하지 못합니다. 매 호출은 백지에서 시작합니다. 그런데 ChatGPT 같은 챗봇은 어떻게 대화를 이어갈까요?

비결: 매번 지금까지의 대화 전체(history)를 함께 다시 보내는 것입니다. "기억"처럼 보이는 건 사실 매 호출마다 과거 대화를 되먹여주기 때문입니다.

1턴:  [user: 안녕]                                   → [assistant: 안녕하세요]
2턴:  [user: 안녕][assistant: 안녕하세요][user: 아까 뭐랬지?]  → 과거를 보고 답함
      └──────────── 이 전체를 매번 다시 보냄 ────────────┘

이 모듈의 ChatBot 클래스는 바로 이 history 관리를 대신해줍니다.

ChatBot 클래스

from typing import List
import init_env, variables
init_env.set_environment_variables()

from gen_ai_hub.orchestration_v2.models.llm_model_details import LLMModelDetails
from gen_ai_hub.orchestration_v2.models.message import ChatMessage, SystemMessage, UserMessage
from gen_ai_hub.orchestration_v2.models.template import Template, PromptTemplatingModuleConfig
from gen_ai_hub.orchestration_v2.models.config import ModuleConfig, OrchestrationConfig
from gen_ai_hub.orchestration_v2.service import OrchestrationService

class ChatBot:
    def __init__(self, orchestration_service: OrchestrationService):
        self.service = orchestration_service
        self.template = Template(template=[
            SystemMessage(content="You are a helpful chatbot assistant."),
            UserMessage(content="{{?user_query}}"),
        ])
        self.llm = LLMModelDetails(name="gpt-5.6-sol")
        self.prompt_template = PromptTemplatingModuleConfig(prompt=self.template, model=self.llm)
        self.config = OrchestrationConfig(modules=ModuleConfig(prompt_templating=self.prompt_template))
        self.history: List[ChatMessage] = []

    def chat(self, user_input):
        response = self.service.run(
            config=self.config,
            placeholder_values={"user_query": user_input},
            history=self.history,          # ← 이전 대화 전달
        )
        message = response.final_result.choices[0].message
        self.history = response.intermediate_results.templating   # ← history 갱신
        self.history.append(message)
        return message.content

    def reset(self):
        self.history = []

service = OrchestrationService(api_url=variables.AICORE_ORCHESTRATION_DEPLOYMENT_URL)
bot = ChatBot(orchestration_service=service)

핵심 두 줄 (메모리의 전부)

  • history=self.history → run() 에 지금까지의 대화를 함께 넘깁니다. 이게 "기억"의 정체입니다.
  • self.history = ...; self.history.append(message) → 이번 질문과 방금 받은 답변을 history에 쌓습니다. 다음 호출 때 또 통째로 넘기려고요.
  • reset() → history를 비우면 기억이 사라집니다 (새 대화 시작).

대화해보기

print(bot.chat("Hello, are you there?"))
print(bot.chat("Do you like SAP CodeJams?"))
print(bot.chat("Can you remember what we first talked about?"))   # 기억해야 함!

bot.reset()
print(bot.chat("Can you remember what we first talked about?"))   # 리셋 후엔 기억 못 함

직접 바꿔보기 (실험)

  • reset() 전후로 "처음에 뭐라고 했지?"를 물어 메모리 유무 체감
  • system 프롬프트를 바꿔 챗봇 페르소나 지정 (예: "SAP 전문 상담원")
  • 모듈 4의 그라운딩 config를 이 챗봇에 결합해 "기억하는 지식봇" 만들기 (심화)

  • reset() 후에는 기억하지 못한다

SAP Generative AI Hub 핸즈온 — 4시간 (실습자용)

SAP AI Core의 Generative AI Hub를 Python SDK로 다루는 4시간 실습입니다. LLM 호출 → 임베딩 → Orchestration → Document Grounding → RAG → 메모리 챗봇까지 코딩 중심으로 진행합니다.

기반 자료: SAP-samples/generative-ai-codejam

🤔 Generative AI Hub가 뭔가요? (한 문단 요약)

여러 회사(OpenAI, Anthropic, Google …)의 LLM을 각각 따로 계약·연동하지 않고, SAP AI Core 안에서 하나의 SDK로 통일해서 쓰게 해주는 서비스입니다. 핵심 장점 세 가지만 기억하세요.

  1. 모델 교체가 코드 한 줄 — gpt-5.6-sol → anthropic--claude-4.6-sonnet 로 이름만 바꾸면 됩니다.
  2. Orchestration — 프롬프트 템플릿·콘텐츠 필터·개인정보 마스킹·문서 그라운딩을 선언형 설정 하나로 묶습니다.
  3. Document Grounding — RAG(문서 기반 답변)를 직접 구현하지 않고 관리형으로 씁니다.

이 네 시간 동안 위 세 가지를 직접 코드로 경험합니다.

이 과정의 전제

  • 단일 공유 AI Core: 강사가 구성한 하나의 AI Core 인스턴스를 전원이 공유합니다. Orchestration·LLM·임베딩 배포는 이미 되어 있고, 여러분은 배포를 만들 필요가 없습니다.
  • SDK 중심: 실습은 Launchpad 클릭이 아니라 노트북에서 SDK 코드를 작성/실행하는 방식입니다. (UI 실습은 보너스/데모로만)
  • 여러분이 할 일은 강사가 공유한 연결 값을 variables.py 에 넣고, 노트북 셀을 실행하며 코드를 바꿔보는 것입니다.

💡 코딩이 처음이어도 괜찮습니다. 모든 코드 셀은 그대로 복사·실행하면 동작하도록 되어 있습니다. 실습의 진짜 재미는 "직접 바꿔보기" 에서 값 하나를 바꿔보고 결과가 어떻게 달라지는지 관찰하는 데 있습니다.

5b. 데이터 마스킹 (PII 익명화)

🧑‍🏫 필터가 "유해성"을 본다면, 마스킹은 개인정보를 모델에 보내기 전에 가립니다. 같은 Orchestration에 masking 모듈을 추가 — "모듈을 끼운다"는 메시지를 한 번 더 강화하는 좋은 예.

💬 이렇게 말하세요: "민감정보를 LLM(특히 외부 모델)에 그대로 보내긴 꺼려지죠. Orchestration이 보내기 전에 이름·이메일·전화번호를 가려줍니다. 규제 산업에선 거의 필수예요."

from gen_ai_hub.orchestration_v2.models.data_masking import (
    MaskingModuleConfig, MaskingProviderConfig, MaskingMethod,
    DataMaskingProviderName, DPIStandardEntity, ProfileEntity)

masking = MaskingModuleConfig(masking_providers=[MaskingProviderConfig(
    type_=DataMaskingProviderName.SAP_DATA_PRIVACY_INTEGRATION,
    method=MaskingMethod.ANONYMIZATION,        # 또는 PSEUDONYMIZATION
    entities=[DPIStandardEntity(type=ProfileEntity.EMAIL),
              DPIStandardEntity(type=ProfileEntity.PHONE),
              DPIStandardEntity(type=ProfileEntity.PERSON)],
)])
service.config = OrchestrationConfig(modules=ModuleConfig(
    prompt_templating=prompt_template, masking=masking))

🧑‍🏫 ANONYMIZATION(복원 불가) vs PSEUDONYMIZATION(가명, 매핑 복원 가능) 차이를 강조. SAP Data Privacy Integration(DPI)이 제공자(DataMaskingProviderName.SAP_DATA_PRIVACY_INTEGRATION).

🎬 데모: PII가 든 프롬프트("내 이름은 홍길동, 이메일 gildong@example.com")를 마스킹 on/off로 돌려 모델에 전달되는 내용이 어떻게 가려지는지 보여주세요. (근거: sap-btp-ai-best-practices 의 data-masking best practice)

모듈 5 · 내 문서 그라운딩 (AI Core Grounding) (강사용)

🎯 목표: 관리형 그라운딩을 내 문서로 확장. 모듈 4(공개)와 대비해 "소스만 바꾸면 된다"를 체득. ⏱️ 시간: 35분 (설명 10분 + 실습 25분) 📓 기반: 노트북 07(Grounding Management, 수집) + 09(SDK 소비)

🧑‍🏫 강사 노트 — 왜 HANA가 아니라 AI Core Grounding인가

이전 버전은 HANA Vector Engine으로 직접 RAG를 짰지만, 단일 공유 AI Core + SDK 중심 전제에선 별도 HANA가 군더더기입니다. 대신 AI Core가 관리하는 벡터 저장소(Document Grounding) 에 문서를 넣고, 모듈 4와 똑같은 SDK 코드에서 필터만 내 저장소로 바꿉니다.

핵심 메시지: "소스는 필터 한 줄." 모듈 4에서 help.sap.com 이던 걸 vector + 내 저장소 id로 바꾸면 끝. 모델 교체가 한 줄이었듯, 지식 소스 교체도 한 줄임을 보여주세요.

역할 분담 (중요)

  • 수집(ingestion)은 SDK 일급 API가 아닙니다. AI Core Grounding의 저장소 생성·문서 적재는 Grounding Management(UI) 또는 Grounding REST API로 합니다. ai_core_sdk 의 "repository"는 Git 저장소(ML ops)라 무관합니다.
  • 그래서 참가자 실습 = 질의(SDK) 에 집중시키고, 수집은 강사가 사전에 처리합니다.

🧑‍🏫 사전 준비 — 공유 벡터 저장소 1개 (강사 1회)

단일 공유 AI Core에 가장 깔끔한 구성:

권장 — 스크립트 1회 실행: 저장소 폴더의 ingest_documents.py 를 쓰면 저장소 생성 → PDF 청킹 → 수집 → 검색 확인까지 자동입니다.

# service key 값을 환경변수로 (AICORE_CLIENT_ID/SECRET/AUTH_URL/BASE_URL)
export AICORE_RESOURCE_GROUP=default
python ingest_documents.py --embedding-model text-embedding-3-small
# → 마지막 줄의 GROUNDING_REPOSITORY_ID 를 참가자에게 공유

이 스크립트는 공식 best-practice(sap-btp-ai-best-practices 의 Document_Grounding_Vector_API)의 흐름을 따릅니다. REST 엔드포인트:

POST /v2/lm/document-grounding/vector/collections                 # 저장소 생성
POST /v2/lm/document-grounding/vector/collections/{id}/documents  # 수집(JSONL)
POST /v2/lm/document-grounding/retrieval/search                   # 검색 확인

(대안: Launchpad Grounding Management UI 로도 동일하게 생성·수집 가능)

수집이 잘 됐는지 코드로 확인:

python inspect_aicore.py collections                       # 저장소·문서 수
python inspect_aicore.py search <repo-id> "data masking"   # 검색되는 청크 확인

참가자별 저장소를 만들 수도 있지만, 읽기 전용 질의라 하나를 공유해도 안전합니다(공개 help.sap.com과 같은 구도). 공유 저장소 1개 = 가장 단순.

🎬 수집 과정을 라이브 데모(화면 공유)로 1~2분 보여주면 "뒤에서 뭐가 일어나는지" 이해가 올라갑니다. 참가자는 따라 만들 필요 없이 id만 받습니다.

Part B. SDK 질의 — 필터만 교체 (참가자 실습)

실습자용의 코드를 함께 실행. 설명 포인트:

filters = [DocumentGroundingFilter(

🎯 목표: 대화 history 전달로 "기억하는" 챗봇 구현 + 지금까지 배운 것 종합. ⏱️ 시간: 20분 (설명 7분 + 실습 13분) — 시간이 밀리면 강사 데모로 축약 가능 📓 기반: 10-chatbot-with-memory.ipynb

🧑‍🏫 강사 노트 — 종합 모듈

여기서 Orchestration이 다시 등장합니다(모듈 3·4). 새 개념은 history(대화 누적) 하나뿐이라, 참가자가 "아 이제 이 패턴이 익숙하다"를 느끼게 하는 통합 단계입니다.

핵심: LLM은 상태가 없다(stateless). 매 호출은 독립적입니다. 그래서 "기억"하려면 이전 대화를 매번 함께 보내야 합니다. history 가 바로 그 누적 대화입니다.

💬 이렇게 말하세요: "모델은 금붕어예요 — 매번 처음 봅니다. '기억'은 사실 우리가 지난 대화를 매 호출마다 다시 넣어주는 거예요. ChatGPT도 내부적으로 이렇게 합니다."

코드 설명 포인트

🧑‍🏫 chat() 메서드의 세 줄이 핵심: 1. history=self.history — 이전 대화를 함께 전달 2. self.history = response.intermediate_results.templating — 서버가 구성한 메시지 목록(히스토리)으로 갱신 3. self.history.append(message) — 이번 모델 답변도 히스토리에 추가

즉 매 턴마다 history가 user/assistant 쌍으로 쌓이고, 다음 호출에 전부 실려 갑니다.

🎬 라이브 데모 (효과 확실): 1. "Hello" → "Do you like SAP CodeJams?" → "Can you remember what we first talked about?" 순서로 호출. 마지막에 "Hello였다"고 답하면 메모리 작동. 2. bot.history 를 출력해 쌓인 대화를 눈으로 확인. 3. bot.reset() 후 같은 질문 → 이제 기억 못 함. "메모리를 비웠으니 금붕어로 돌아간 거죠."

직접 바꿔보기 (실험)

  • reset 전후 비교 (위 데모를 참가자가 직접)
  • 페르소나 변경 (system 프롬프트)
  • ⭐ 종합 과제: 모듈 4의 그라운딩 config를 이 ChatBot의 config 에 넣어 "기억 + 근거" 챗봇 완성. 오늘 배운 모듈 조합의 정점. 시간 되면 꼭 시도.

❓ 예상 질문 & 답

  • "history가 무한정 쌓이면?" → 토큰 한계·비용↑. 실무에선 오래된 대화 요약·윈도우 제한·중요 정보만 추출 등 메모리 관리 전략 사용.
  • "세션별로 분리하려면?" → ChatBot 인스턴스를 사용자/세션마다 하나씩, 또는 history를 외부 저장소(DB)에 세션 키로 보관.
  • "그라운딩이랑 같이 쓰면 history에 context도 쌓이나요?" → 설계에 따라. 보통 질문/답변만 history로, context는 매 턴 새로 검색.
